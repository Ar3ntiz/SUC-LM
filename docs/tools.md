# Evaluation and benchmark tools: `suc eval` and `suc perf`

Two dedicated tools for the finished SUC1 files, modelled on `ds4-eval` and `ds4-bench` of the
[ds4](https://github.com/antirez/ds4) project (MIT License, Copyright (c) 2026 The ds4.c authors). Their logic was
re-implemented in Python for SUC, not translated line by line; the ds4 question set was imported with attribution (see
"Provenance and licenses" below).

| | `suc eval CONFIG` | `suc perf CONFIG` |
|---|---|---|
| Question | Does the compressed model still answer correctly through the real inference path? | How fast is it (prefill, TTFT, decode) and how much memory does it use, next to MLX 4-bit and BF16? |
| Systems | `suc1_cpp` (C++ `suc1-generate`), `suc1_python` (Python/MLX runtime), optional `bf16` / `mlx_affine` | same, all in one session, sequentially |
| Output | `experiments/results/<ts>_<name>.json` + `.md` (same stem) | same |
| Code | `suc/cli/eval.py`, `suc/evaluation/{suite,answers,runners}.py` | `suc/cli/perf.py`, `suc/evaluation/runners.py` |
| Configs | `experiments/configs/eval_*.yaml` | `experiments/configs/perf_*.yaml` |

`suc bench` is unchanged (the Phase 0 baseline runner).

Practical usage guide (quick start, full config reference, grading rules, own suites, reading the outputs, pitfalls,
troubleshooting): [usage_eval_perf.md](usage_eval_perf.md).

## What ds4-eval and ds4-bench do

**ds4-eval** (`ds4_eval.c`) is a regression harness, not a leaderboard: it loads the real model, renders chat prompts,
prefills them, samples token by token and grades the final answer of a small *embedded, audited* question set (92
items: 25 GPQA Diamond, 25 audited SuperGPQA, 25 AIME 2025, 17 COMPSEC C/C++ vulnerability-localization items, in
progressive order). Key ideas:

- every prompt ends with an instruction to write exactly one final line `Answer: <letter | integer | line numbers>`;
- robust extractors grade only the text after `</think>`: the last `Answer:` marker, multiple-choice letters with
  prose/negation filters (`A careful …`, `not B`), integers taken right of the last `=` on the answer line, line sets
  matched against an audited accepted range; a `--self-test-extractors` mode pins the extractor behaviour;
- a thinking-budget controller: a soft limit accepts `</think>` when it is near the top of the distribution, a hard
  limit forces it so that a fixed reserve remains for the visible answer;
- a trace file with every prompt and output, and `--regrade-trace` to re-grade a trace with the current extractor
  without the model (shows which cases changed);
- a deterministic token-count gate (temperature 0, fixed seed: per-question generated-token counts and pass/fail must
  stay equal to a baseline after inference changes);
- a per-question report: state, prompt / generated / total tokens, given and correct answer.

**ds4-bench** (`ds4_bench.c`) measures throughput at context *frontiers* rather than one whole-run average: one fixed
token sequence (a cleaned public-domain text, *I promessi sposi*), frontiers `--ctx-start … --ctx-max` by
`--step-incr` or `--step-mul`, incremental prefill of only the newly added interval on one live session, then a fixed
greedy decode that never stops at EOS, a session snapshot restore, and the next frontier. One CSV row per frontier:
prefill tokens/s, generation tokens/s, first-token ms, steady tokens/s, KV-cache bytes; a stdlib plot script; per-
machine CSVs as the baselines that release QA compares against.

## `suc eval`

**Suites** (`experiments/eval/*.json`, validated by `suc.evaluation.suite.load_suite`; the file sha256 is the
`dataset_hash` of the run):

- `suite_core.json` (40 cases): the 20 QA prompts of `experiments/qa/prompts.json` (raw prompts as before; the 10 math
  prompts are graded on their integer answer, the 10 explanations are `open` = not graded, compared only when a
  reference is set) plus 20 short authored items (10 integer, 10 multiple choice, English and Italian, no thinking,
  ds4-style `Answer:` line). Fast: suitable for every file and every runtime.
- `ds4_subset.json` (67 cases): the ds4-eval set without GPQA Diamond (25 SuperGPQA, 25 AIME 2025, 17 COMPSEC), thinking
  on. Hard and long; generated by `scripts/import_ds4_eval_cases.py` from `ds4_eval.c`.

Case kinds: `choice` (2–10 options, letter key), `integer`, `lines` (accepted line set, e.g. `17-20`), `open`.

**Protocol.** Prompts are rendered once in Python with the checkpoint's chat template (`enable_thinking` per case, or
forced by `think: on|off`) and passed to every system as token ids, so all runtimes see identical tokens. Decoding is
greedy (no sampling: the C++ sampler is not mlx-lm's RNG, and greedy makes reruns reproducible); a case stops at an
EOS id of the tokenizer or at its token budget (`max_tokens` of the case, capped by the config's `max_tokens`).
Thinking budget: ds4's hard limit, adapted to stateless runners — a thinking case first runs `budget −
think_reply_reserve` tokens; if it did not stop and did not close `</think>`, `</think>\n\n` is forced and the reserve
follows (`think_close: hard` in the record); ds4's soft limit (rank-based early close) is not implemented because it
needs per-step logits from the pipelined C++ decode.

**Grading** (`suc.evaluation.answers`): a port of the ds4 extractors with the ds4 self-tests as unit tests
(`tests/unit/test_eval_answers.py`); SUC additions for prompts without an `Answer:` line: the last `\boxed{…}` is
preferred over loose markers, thousands separators are kept (`1,024`).

**Reference comparison (optional, off by default).** The core is grading the SUC1 model itself. With
`reference: <system name>` (e.g. a `bf16` or `mlx_affine` system) every other system additionally gets, per case:
identical output, common token prefix and first divergence, answer agreement, and teacher-forced metrics on the first
`teacher_forced_positions` tokens of the reference output (next-token KL(ref ‖ system), top-1 agreement, NLL of the
reference tokens under both).

**Replay and drift.**
- `suc eval --regrade RESULT.json` re-grades the stored outputs with the current extractors (no model) and prints the
  cases whose state or picked answer changed (ds4 `--regrade-trace`).
- `compare_to: RESULT.json` in the config reports, per system and case, changes of state, picked answer, generated-token
  count and token-sequence hash (ds4's deterministic gate). On the same machine and software a greedy rerun must give
  zero changes; across runtimes (C++ vs Python) small rounding differences can move long generations.

**Result.** JSON: metadata (git, runtime, model hash, suite sha256, seed, config hash), the selected cases, per system
`info` (kind, file sha256 and size, load time, resident bytes), per case records (status PASSED / FAILED / UNGRADED /
ERROR, picked / expected, prompt and generated tokens, think_close, full text and token ids, seconds, decode ms/token)
and a summary (pass rate overall and by source); optional agreement / drift. The `.md` next to it has the summary, the
per-source table, a per-case table (state, generated tokens, answer per system) and, with a reference, the per-case
agreement table. Runner errors are recorded (`ERROR`) and the run continues (unattended).

## `suc perf`

**Protocol** (same for every system, one session, sequentially): the prompt file is tokenized raw (no chat template);
for every context length (`contexts: [...]`, or ds4-bench frontiers `ctx_start`, `ctx_max` with `step_incr` or
`step_mul`) and batch size, `warmup` untimed runs (8 tokens) and `repeats` timed runs of: a full prefill of the context
from an empty cache, then `gen_tokens` greedy tokens with EOS ignored. Per run: prefill tok/s = B·ctx / prefill time,
TTFT = prefill until the first token is available, decode ms/step = median of steps 2…n (step 1 reported separately as
"first step"), p90; per row: median / mean / stdev / min / max / CV over the repeats, peak memory, KV-cache bytes, and
whether the first generated tokens were identical across repeats. Batch b uses b different windows of the text
(overlapping when b·ctx exceeds it).

- mlx-lm systems (BF16, MLX affine, Python SUC runtime): chunked prefill (`prefill_step_size`, 2048 as
  `mlx_lm.generate_step`), decode `pipelined` (the next step is queued with `mx.async_eval` before the current token is
  read, as mlx-lm and the C++ pipelined decode do; default) or `sync`. Memory = MLX peak of the run (weights included).
- C++ (`suc1-generate`): one process per run; file mapping and Metal pipeline compilation are outside the timing
  windows (reported as `load_s`, `compile_s`); its own prefill (batch, `--chunk` 64) and pipelined decode; memory =
  mapped file + process `phys_footprint` (+ KV, arena). Batch 1 only: larger batches are recorded as `unsupported`.

Differences from ds4-bench: every row is a fresh full prefill (no session snapshot API in the C++ tool), repeats with
statistics, several systems in one session with ratios against `reference`, and `compare_to` (or
`suc perf CONFIG --compare-to OLD.json`) for row-by-row new/old ratios of decode tok/s, prefill tok/s and TTFT.

**Validity.** Timings are only comparable within one session on one otherwise idle machine; the top CPU processes at
the start are recorded (`other_processes`). Benchmarks of record come from the Mac Studio; laptop numbers are
indicative. Do not run `suc perf` in parallel with anything else (CLAUDE.md).

**MLX decode mode matters.** The earlier MLX decode figures in benchmarks.md come from synchronous per-token evaluation
(`suc.evaluation.speed`, the e2e harness), which is slower than how mlx-lm itself decodes. Laptop check (Qwen3-0.6B,
MLX affine 4-bit g64, Apple M3, 128-token prompt, uncommitted code, indicative): `mlx_lm.stream_generate` 203 tok/s
(4.9 ms/token); `suc perf` pipelined 4.92–5.15 ms/step; `sync` 6.47–6.50 ms/step. Compare SUC with the pipelined MLX
figure (the default), since the C++ decode is pipelined too.

## Commands

Laptop (Apple M3, dev model, SUC1 files on the local disk):

```bash
HF_HUB_OFFLINE=1 .venv/bin/suc eval experiments/configs/eval_qwen3_0.6b_final.yaml
HF_HUB_OFFLINE=1 .venv/bin/suc perf experiments/configs/perf_qwen3_0.6b_final.yaml
.venv/bin/suc eval --regrade experiments/results/<ts>_eval_qwen3_0.6b_final.json
```

Mac Studio (code via `git push studio main`; results committed on the Studio and pulled back, CLAUDE.md "Machines").
Run sequentially, one tool at a time; each line can be queued in one `nohup` script under `logs/`:

```bash
ssh <user>@<studio-host>
cd ~/Projects/SUC-LM
# Qwen3-8B, final file (core suite: C++ fused / separate + Python runtime), then speed vs MLX 4-bit and BF16
HF_HUB_OFFLINE=1 nohup .venv/bin/suc eval experiments/configs/eval_qwen3_8b_final.yaml > logs/eval_8b_final.log 2>&1 &
HF_HUB_OFFLINE=1 nohup .venv/bin/suc perf experiments/configs/perf_qwen3_8b_final.yaml > logs/perf_8b_final.log 2>&1 &
# Qwen3-30B-A3B, greedy and uniform final files
HF_HUB_OFFLINE=1 nohup .venv/bin/suc eval experiments/configs/eval_qwen3_30b_a3b_final.yaml > logs/eval_30b_final.log 2>&1 &
HF_HUB_OFFLINE=1 nohup .venv/bin/suc perf experiments/configs/perf_qwen3_30b_a3b_final.yaml > logs/perf_30b_final.log 2>&1 &
# optional, long (thinking up to 8192 tokens × 67 cases): the hard ds4 suite
HF_HUB_OFFLINE=1 nohup .venv/bin/suc eval experiments/configs/eval_qwen3_8b_final_ds4.yaml > logs/eval_8b_final_ds4.log 2>&1 &
HF_HUB_OFFLINE=1 nohup .venv/bin/suc eval experiments/configs/eval_qwen3_30b_a3b_final_ds4.yaml > logs/eval_30b_final_ds4.log 2>&1 &
# afterwards
git add experiments/results && git commit -m "eval/perf results"
```

(Wait for each job before starting the next — e.g. one script that runs the lines without `&` one after the other.)
The C++ tool must be built on the Studio (`cpp/build.sh ~/suc-local/cpp-build`, the default `cpp_build`). For a BF16
comparison in `suc eval`, uncomment the `bf16` system in the config and set `reference: bf16`.
